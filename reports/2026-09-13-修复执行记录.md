## 执行中新发现的问题（审计未收录）

1. **CRASH-04（High）——`MiddlewareBase.FireEvent` 无限自我递归 → 栈溢出**。`FireEvent` 实现为 `m.First().FireEvent(e)`，而 `First()` 在 `pre == nil` 时返回 `m` 自身，于是链头不是 `NetMiddlewareFirst` 的任何情形都会无限递归。**Go 的栈溢出是 fatal error，`recover` 拦不住**，比 nil panic 更糟（绕过 `recoverPanic`/`safeAccept` 的全部兜底语义）。已加守卫并在 `engine/net/middleware/middleware_test.go` 用崩溃探针钉住。
2. **我自己的 Phase 1 修复引入了两处重入死锁，均被新测试抓到并修掉**：
   - `netServer` 的清理闭包在派发 OnDisconnect 时调 `this.onDisconnect(s)` **未判空** → 未设置回调的用法 nil panic（`TestNetServer_Stop_ClosesAllSessions` 立刻变红）。已给四个回调全部补判空，且 `RemoveSession` 不受回调缺失影响。
   - `inclient.ClientMgr.CloseAllClient` **持 `m.mu` 调 `Disconnect()`** → 断开通知重入 `RemoveClient` 取同一把锁 → 自死锁。已改为锁内快照、锁外断连，并加了超时看门狗用例 `TestClientMgr_CloseAllClient_DoesNotDeadlock`。
3. **`AcceptorSocket.Start` 会复活被 Stop 的监听**：最初版本的循环顶部重读 `this.listener`、为 nil 就 `Listen()`，而 `Stop()` 恰恰置 nil → Start 自己把端口重新占上继续 accept，Stop 失去终止语义。由新增的 `TestAcceptor_StartReturnsAfterStop` 发现，已改为「入口绑定一次、循环内不再重绑」。
4. **CRASH-01 的原判断被证伪（重要更正）**：报告称「修好 SEC-01 会让 `OnDisconnect` 里 `GetConn().RemoteAddr()` 必然 panic」。用「只还原 `session.go`、保留 SEC-01 修复」的对照实验证伪——`Close()` 是**先** `Disconnect()` **后**置 nil，而断开通知在 `Disconnect()` 内同步跑完，回调看到的 conn 仍非 nil。该条由 Critical 降级为 High；**数据竞争是真实的**（`-race` 在未加锁版本上当场报出 `WARNING: DATA RACE`），`Close()` 后置 nil 也只是 API 陷阱。
5. **M-11 的自死锁从推导变为实证**：只还原 `TravelSession`（保留 `Len()`）后，`TestSessionMgr_TravelSession_CallbackMayRemove` 精确在 5.00s 超时命中「持 RLock 期间取写锁」——确认这不是假设。
6. **e2e 测试的启动竞态（测试 bug，非产品 bug）**：`go svr.Start()` 后立刻 `go cli.Start()`，客户端可能在服务端 bind 完成前拨号；`outclient.Start()` 无内部重试（重试在 `cmd/client.go` 的死循环里）→ `-race` 下确定性建不起隧道。已改为分阶段等待端口就绪 + 与入口同构的重试循环。
7. **`L-9` 从「低风险 API 陷阱」升为实测 DATA RACE**：遗留 goroutine 在 `OnDisconnect` 里读 `log.Main()` 与下一用例的 `SetMainLog` 并发，`-race -count=2` 稳定复现，已用 `atomic.Pointer` 修掉。

### 本轮新抓到的真实缺陷

**1. 我在 Phase 1 自己引入的数据竞争（已修）。** `fireDisconnect()` 无锁读 `onDisconnectFunc`，而 `SetOnDisconnect` 在 accept/拨号 goroutine 上写它。改之前该字段只被 `receiverRun`/`senderRun` 读取——它们在 setter 之后由 `go` 语句建立 happens-before，所以是安全的；但 SEC-01 修复让**任意 goroutine** 的 `netSession.Close() → Disconnect() → fireDisconnect()` 也会读这个字段，原先的保证就此失效。

新增的 `TestNetServer_OnAcceptPanic_ReclaimsSession` 以 **37%（3/8 轮）**的概率打出 `WARNING: DATA RACE`。修法：`ConnSocket` 增加 `cbMu sync.RWMutex` 保护两个回调字段，写者持写锁、读者取出快照后立即解锁再调用（`receiverRun` 入口取一次 `onData` 快照，避免每帧过锁）。修复后同用例压测 **10/10 轮 ×3 次运行全绿**，全套 `-race` 连跑 3 次 22/22。

**教训**：给一个字段新增读取路径，等于重新审视它所有的写入方。这次是"让清理在所有路径都跑起来"这个正确目标，顺带把一条原本靠调度顺序侥幸成立的隐式契约打破了。

**2. L-8 从"API 陷阱"升格为实际崩溃。** 我本轮为 M-18 新写的 `inserver.replyCode` 用了 `s.GetConn().RemoteAddr()`，而 `GetConn()` 可能返回 nil —— 新加的测试立刻把它打成 nil 解引用 panic（`inserver.go:88`）。审计里这条被写成"无实测触发路径"的 Low，判断偏轻：`inserver.go` 共 **13 处**同样的裸链式调用，且全部集中在**日志与错误分支**，也就是排障最需要日志能活着的时候。

已统一改为防护助手 `remoteAddr(s)`（会话为 nil、conn 为 nil 时返回占位串而非 panic），13 处全替换。

**3. M-14 部分已被顺带解决，但没全解决。** 原报告称"`onAccept` panic 时 session 已注册进 map → 留下永久孤儿条目"。实测：Phase 1 之后 `safeAccept` 的 recover 调 `Abort()`，`Abort()` 现在会派发断开通知，而通知闭包里含 `RemoveSession` —— **孤儿会话已被回收**，新增 `TestNetServer_OnAcceptPanic_ReclaimsSession` 钉住这个行为（防止将来有人改掉 `Abort` 的通知语义）。

但 M-14 的第二半**仍然存在**：`onAccept` 与 `FireEvent(OnConnect)` 依然在 accept 循环内同步执行，一个慢/阻塞的 onAccept 会**头阻塞该公网端口的所有新连接**。要修需把它们移出循环，而这会改变 `OnConnect` 的执行 goroutine、必须重新核对 type1 握手的并发契约——因此仍未做，见下表。

### 一条自我更正：M-12 的第一版守卫是错的

我最初把守卫写成"`Connect` 失败或断开后**回落 Idle**，因此可以重连"。两处都错了：

1. **语义上重新引入了它要防的 bug**——再次 `Connect()` 就是对**同一个** `ConnectorSocket` 二次拨号并覆盖底层 `conn`，旧 fd 与两个 goroutine 照样泄漏。守卫留了这个后门等于没修。
2. **它让我自己写的用例变 flaky**：3 次里挂 2 次（`TestNetClient_FullLifecycleWithHandshake`）。

正确模型是**单实例单连接**：新增终态 `stateDone`，`Connect` 只允许从 `Idle` 发起一次，失败与断开都落终态，重连必须构造新实例（`cmd/client.go` 的重连循环本来就是这么写的）。

连带修正：`e2e` 的重连循环原先在每轮复用同一个 `outclient`，在终态语义下从第二轮起会一直报 "not idle"、隧道再也起不来——已改为每轮新建实例并用互斥锁保管"当前实例"供清理函数 Stop。修正后该用例与 e2e 一起 `-count=4` 连压 3 轮全绿。

**教训**：flaky 用例往往不是测试写得糙，而是实现留了个自相矛盾的口子。这次若只给用例加 `sleep` 或重试把它"哄绿"，就会把后门留在生产代码里。

### 一条经核实不成立的计划项：TCP_NODELAY

计划里的 `SetTCPNoDelay(true)`（以及审计中"未设 TCP_NODELAY 致交互式协议延迟受损"）**不成立**：Go 标准库 `net/tcpsock.go` 的 `newTCPConn` 第一行即 `setNoDelay(fd, true)`，拨号与 accept 出来的每条 TCP 连接都经过它，因此 **TCP_NODELAY 本就默认启用**。已从计划与文档中撤回该项（未新增任何代码——加一行只是噪音）。
