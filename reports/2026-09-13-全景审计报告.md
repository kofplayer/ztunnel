## 一、根因视图

本次绝大多数 Critical/High 不是 20 个孤立缺陷，而是 **4 个根因**的投影：

```
根因 A  「关闭」语义被一个守卫混淆        根因 B  type1 密码学实现有三处独立失效
  !q.IsClose() 被当作"已通知断开"            移位 bug + math/rand + 公开置换表
  ├─ SEC-01 预认证僵尸 outserver/内存泄漏      ├─ CRYPT-01 有效熵 15 bit  [已实证]
  │         [已实证]                          ├─ CRYPT-02 密钥源非 CSPRNG  [已复核]
  ├─ LEAK-01b 正常路径用户会话泄漏             └─ CRYPT-03 Key1 等同明文    [已复核]
  ├─ CRASH-01 修 A 即引爆 nil panic（耦合）    → 结论：-net_encrypt=true 可被被动解密
  └─ Stop() 后 map 仍满                    → 根因 D 默认配置把所有攻击面拉满
根因 C  生命周期缺少所有权与上限              (-token="" / -net_encrypt=false / 无鉴权即监听任意端口)
  ├─ LEAK-02 senderRun 写失败裸 return
  ├─ LEAK-03 outclient.Stop 不断控制连接     这三条根因互相掩盖：修 A 会暴露 CRASH-01；
  ├─ LEAK-04 listener 无 recover/无退避      修 B 会暴露 CRYPT-02/03；所以必须按批次推进，
  ├─ DOS-01  无握手超时/无连接上限            见《修改执行计划》的分批设计
  ├─ DOS-02  OpenClient 同步拨号头阻塞
  └─ DOS-03  用户一连上即拨内网，无每隧道上限
```

## 二、Critical

### SEC-01 主动关闭被单个守卫整体吞掉，业务清理永不执行 `[已实证]`

**位置**：`engine/net/connect/socket/conn.go:72` 与 `:80`（守卫）、`engine/net/server/server.go:112`（唯一清理点）、`common/server/server.go:32-38`（触发方）

`RemoveSession` 在全项目**只有一个生产调用点**，挂在 `conn.SetOnDisconnect` 回调里；而该回调的两处调用点都被 `if !this.q.IsClose()` 守卫。`netSession.Close()` → `conn.Disconnect()` → `q.Close()` 使队列先关闭，于是等 err 传回 `receiverRun` 时守卫恒为假 —— **整条 OnDisconnect 链（中间件事件 + 业务回调 + RemoveSession）被完全跳过**。

`q.IsClose()` 实际表达的是"队列已关"，被误用为"断开已通知"。这两件事在被动断开时恰好等价，在主动关闭时完全背离。

三条已确认的泄漏路径：

| 路径 | 触发 | 后果 |
|---|---|---|
| 预认证 | 连上 `:8888` → 发 `CreateTunnel`（默认空 token 恒过）→ 再发任意畸形帧 | handler 返回 error → `s.Close()` → `inserver.OnDisconnect` 不执行 → `outServer.Stop()` 不执行 → **export 端口的 listener 永久僵尸化**，控制会话永久留在 map（其 `bindObject` 钉住整个 outserver 对象图） |
| 正常业务 | 内网服务先关（MySQL `wait_timeout`、HTTP keep-alive 超时）→ client 发 `ConnectDelete` → `inserver.go:123` `session.Close()` | outserver 的用户会话条目永久残留；长跑进程内存稳定爬升 |
| 跨进程 | 控制通道断开 → `outServer.Stop()` → `TravelSession` 里 `s.Close()`（主动） | 用户会话的 OnDisconnect 被跳过 → **`ConnectDelete` 永不发给 client** → 内网 client 到真实服务（示例配置 MySQL:3306）的连接永久不释放 |

端口僵尸化还会二次伤害：合法 client 的 10s 重连循环对该端口永远 `EADDRINUSE` → 收到错误码 → 再重连 → **直到重启服务端都不能恢复**。

**复现**：`reports/evidence/LEAK-01_probe_test.go`（拷回 `server/inserver/` 运行）。实测输出：

```
泄漏：控制会话仍留在 sessionMgr 中，数量=1（期望 0）
僵尸 listener：export port 56667 仍被占用，outserver.Stop() 从未执行
```

### CRYPT-01 type1 掩码移位 bug：每包密钥有效熵只有 15 bit `[已实证]`

**位置**：`engine/net/middleware/encrypt/type1/base.go:143`

```go
masks[i] = uint8((key >> i) & 0xFF)        // 现网：按 bit 位移
masks[i] = uint8((key >> (i * 8)) & 0xFF)  // 应为按字节位移
```

同文件的概念对应函数 `GetKeyBytes:46` 用的正是 `key >> (i * 8)`，可见这是笔误而非设计。`i` 取 0..7，掩码字节只覆盖 `key` 的 bit0..bit14，**高 49 bit 完全丢弃**。

**实测**（`reports/evidence/CRYPT-01_mask_entropy.go`）：64 位 key 空间只产生 **32768 种不同掩码**；且低 15 bit 为 0 的 key（概率 1/32768）产生**全零掩码，该连接数据原样明文直通**。已知明文或 verifier 的 XOR 和即可离线穷举出某包掩码，配合 `GoNextCsNo/GoNextScNo` 只依赖低位的特性可递推该方向后续全部包。

### CRYPT-02 全部会话密钥来自 `math/rand` `[已复核]`

**位置**：`base.go:9`（`import "math/rand"`）、`base.go:39-41`（`GenKey() { return Key(rand.Uint64()) }`）

`Key1`、`Key2`、`CsNo`、`ScNo` 四个全部密钥材料都由非线性密码学的全局 `math/rand` 生成；同文件里 `crypto/rand` 只以别名用于 RSA-OAEP 的 salt。grep 确认**全仓库仅这一处 `math/rand`**，也就是唯一必须用 CSPRNG 的地方用错了包。Go 文档明确要求"保存不可预测秘密的程序必须用 crypto/rand"。

### CRYPT-03 Key1 由源码中公开的置换表保护，等同明文传输 `[已复核]`

**位置**：`base.go:16-17`（`enTable`/`deTable` 为硬编码公开常量）、`:64-74`、`client.go:101-110`、`server.go:68-69`

首帧 8 字节承载 Key1，保护手段是查这张在发行源码里可读的固定表。被动观察者逐字节查 `deTable` 即还原 Key1 全 64 bit，零计算成本。且握手帧经 `m.Pre().SendData` **绕开了 verifier**（栈序 `len4 → type1 → verifier`，校验字节在加密层之内），首帧无任何完整性保护或 transcript 绑定 —— 改一位首帧即等于攻击者指定 Key1，双方照常握手成功。

**三条叠加后的净结论**：`-net_encrypt=true` 提供的保护**低于文档当前声称的"仅能对抗被动窃听"** —— 被动观察者即可解密整条会话。这句文档表述应当撤销。根治方案是迁移 `crypto/tls` + 自签证书 + 公钥指纹 pinning（全标准库，仍满足零第三方依赖硬约束）。

### LEAK-02 `senderRun` 写失败后裸 return，不关 socket 也不通知 `[已复核]`

**位置**：`engine/net/connect/socket/conn.go:97-105`

```go
msg := data.([]byte)
for len(msg) > 0 {
	n, err := this.conn.Write(msg)
	if err != nil {
		return          // 不 conn.Close()、不 q.Close()、不 onDisconnectFunc()
	}
	msg = msg[n:]
}
```

全仓库只有两处会 `conn.Close()`：`senderRun:94`（队列排空退出）和 `Abort()`（仅 recover 路径）。写错误后 `senderRun` 退出而 `q` 仍未关闭 → ① **fd 永久泄漏**（后续 `Disconnect()` 只关队列）；② `SendData`/`Enqueue` **永远返回成功**，业务以为已发出，实际全部堆积在无人消费的 ring buffer 里；③ 若对端半关闭，`receiverRun` 永久阻塞在 `Read` → 2 个 goroutine + 1 个 fd 全泄漏。`recoverPanic:111-123` 是同构场景，那段代码做对了 —— 照它写即可。

### LEAK-03 `outclient.Stop()` 从不断开控制连接 `[已复核]`

**位置**：`client/outclient/outclient.go:74-78`

```go
func (c *outClient) Stop() error {
	c.c <- true                     // 只解除 Start 的阻塞
	c.inClientMgr.CloseAllClient()  // 只关 inclient
	return nil                      // 从未 c.cli.Disconnect()
}
```

`createTunnelTimeout` 的 10s 定时器到期（`:102`）走这条路：控制连接**保持 ESTABLISHED**，其 receiver/sender 两个 goroutine 常驻，服务端侧会话也认为对端活着并继续持有 export 端口。`cmd/client/client.go:43-53` 随后新建 client 重连 → 该端口 `EADDRINUSE` → 错误码 → 又一条僵尸控制连接。**每轮重连泄一条，永久不自愈，最终两端 fd 耗尽。**

注意：`ErrorCodeNormal` 分支不泄漏（handler 返回 error 会让 `receiverRun` 正常关闭），泄漏专属超时分支 —— 也就是"服务端慢应答"这一最常见场景。

### CRASH-01 `netSession` 四个字段完全无锁；`Close()` 还把 `conn` 置为 nil `[已实证 — 并修正原判断]`

**位置**：`engine/net/session/session.go:70-77`（`ns.conn = nil`）、`server/inserver/inserver.go:55`（`s.GetConn().RemoteAddr()`）、`inserver.go` 另有 11 处 `s.GetConn()`

```go
func (ns *netSession) Close() error {
	if ns.conn != nil {
		err := ns.conn.Disconnect()
		ns.conn = nil        // 无锁写
		return err
	}
```

`conn` / `bindObject` / `sendMessageFunc` 三个字段没有任何同步。可达竞态：`inserver.go:110/125` 从**控制通道 receiver goroutine** 写用户会话的 `ns.conn`，同一时刻该用户连接自己的 receiver goroutine 正在读它。

**⚠️ 执行阶段的更正**：本条原被列为 Critical，理由是"修好 SEC-01 会让 `OnDisconnect` 里的 `GetConn().RemoteAddr()` 必然 nil panic"。用三组对照实验证伪了这条推导 —— `Close()` 是**先** `Disconnect()`、**后** `ns.conn = nil`，而断开通知是在 `Disconnect()` 内部**同步**执行完的，所以回调看到的 `conn` 仍非 nil。必然 panic 这条路**不可达**。

真正成立的两点：
1. **数据竞争是真实的** —— 在未加锁版本上用 `-race` 跑并发访问用例，当场报出 `WARNING: DATA RACE / Write at ... Previous write at ...`。这也解释了为什么既有 48 个用例全绿却仍有此问题：**`testutil/fakenet.go` 的 `FakeSession` 给所有字段都加了 `mu`，测试桩的并发契约比生产实现更严格**。
2. `Close()` 后置 nil 使 `GetConn()` 在会话关闭后返回 nil 接口，属 API 陷阱（`inserver.go` 有 11 处裸 `s.GetConn()`），任何"稍后再取连接地址"的新代码都会踩。

严重性据此下调为 **High**。仍建议与 SEC-01 同批修，但理由改为：不加锁会让 SEC-01 修复后新增的并发派发路径放大这个既有竞态窗口。

### DOS-01 无握手超时 + 无连接数上限 `[待复核]`

`engine/net/client/client.go:134` 的 `return <-result` 无 `select` 超时；`engine/net/connect/socket/acceptor.go:44-58` accept 后不 `SetReadDeadline`；`sessionMgr` 无上限。对端完成三次握手后静默（或只喂半帧），服务端的会话 + 2 个 goroutine + 整条中间件实例即永久驻留 —— **未认证远程资源耗尽**。TCP keepalive(30s) 杀得死死对端，杀不死"活着但不握手"。客户端侧 `Connect()` 可无限阻塞，`outClient.Start()` 挂死并泄漏三个 goroutine。

此项与 CLAUDE.md 已记录的"无读写超时"部分重叠，但**已记录项描述的是稳态连接，这里是预认证握手阶段**，攻击面与修复方式都不同，需单列。

## 四、Medium

**协议与状态机**

| ID | 问题 | 位置 |
|---|---|---|

## 七、明确排除的怀疑点（避免后续重复调查）

以下经逐分支推演/核对确认**不是问题**：

- **ring buffer 扩容与回绕正确性**：`size=2` 起全路径推演（含 `count==size ⇒ head==tail` 不变式、`PushBatch` 的 `size-count<n` 预扩容、`Pop` 清零引用），无越界、无顺序错乱、无 lost update。
- **`Queue.Receive` 的 `Signal()` 在 Unlock 之后**：等待方用 `for` 复查谓词，不构成丢失唤醒；多消费者下单 `Signal` 正确。`Close` 后仍可排空存量、重复 `Close` 幂等，均符合文档声明。
- **`len4Data`/`len2Data` 的接收拷贝**确实切断了 `buf[4096]` 复用带来的别名；`uint64` 长度计算 + `MaxFrameSize` 使 `0xFFFFFFFF+4` 回绕路径不可达。
- **`netServer` 中 `SetOnData/SetOnDisconnect` 与收发 goroutine 的可见性**：两条路径的字段写都严格发生在对应 `go` 语句之前，happens-before 成立，**不存在这条竞态**。
- **type1 `mu`/`sendMu` 分工的主体**：在"每连接单接收 goroutine"模型下，所有对 `Key1/Key2/CsNo/ScNo` 的跨 goroutine 读写都被 status 检查 + `mu` 的 happens-before 链正确串行化；`FireEvent` 在锁外调用也确实规避了 `SendData` 重入 `mu` 的自死锁（`sync.Mutex` 不可重入）。**唯一漏洞是 PROTO-01 那个"握手最后一帧绕开 sendMu"的窗口。**
- **跨隧道 connectId 伪造**：`bindOutServer` 只取本控制会话绑定的 outserver，每个 outserver 独立 sessionMgr → client **无法**伪造别人的 connectId；乱序/伪造只能伤害自己隧道的用户。这一层隔离是对的。
- **恶意 client 让 server SSRF 到内网任意 host:port**：**不能** —— 协议里没有让 server 指定 forward 的字段，`forward` 只来自 client 自己的 flag。真正的内网侧新风险是反向的（M-02：恶意 server 让 client 无限拨内网）。
- **RSA 公钥降级攻击**：实测 Go 1.24 的 `rsa.EncryptOAEP` 会拒绝 `e=1`（"public exponent too small"）与 1023-bit 模数（"N-bit keys are insecure"），降级被标准库挡住。但 `x509.ParsePKIXPublicKey` 本身**接受**这两种弱公钥，防线完全依赖 stdlib 的隐式下限 → 见 M-23。

## 九、总体判断

项目分层与文档质量都相当高（渐进式披露的 CLAUDE.md 体系、崩溃探针回归模式、`-race` 全量可跑），上一轮加固也确实把最显眼的未认证崩溃和缓冲别名问题修干净了。但本轮暴露出一个模式：**`a469546` 的修复集中在"解析前校验长度"和"判空"这类点状加固，而真正的系统性风险在生命周期与所有权上** —— SEC-01/LEAK-02/LEAK-03/M-12/M-14/M-15 六个问题本质都是"关闭/重连没有唯一所有者的幂等路径"，只是散在六个不同文件里。SEC-01 已实证，一条预认证连接即可永久占死一个公网端口。

加密层的结论更值得优先处置：CRYPT-01 是一个**单字符笔误**（`>> i` vs `>> (i*8)`），叠加 CRYPT-02/03 后，`-net_encrypt=true` 的实际保护是"可被被动解密的混淆"，而文档与用户预期都是"加密"。这个认知差距比任何单条缺陷都危险。

好消息是三个根因都有明确、低风险的收口方式，且大部分修复不需要改协议：见《2026-09-13-修改执行计划.md》。
