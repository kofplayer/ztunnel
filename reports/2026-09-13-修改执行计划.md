# ztunnel 修改执行计划

- 日期：2026-09-13
- 依据：`reports/2026-09-13-全景审计报告.md`（问题 ID 与本报告一一对应）
- 证据：`reports/evidence/LEAK-01_probe_test.go`、`reports/evidence/CRYPT-01_mask_entropy.go`

## 分批原则

批次划分不按"严重程度"，而按**兼容性风险**与**互相引爆关系**：

1. **协议兼容优先隔离**：CRYPT-01 的修复会改变线上掩码 → 新旧版本互不通。绝不能和零风险改动混在一个提交里。
2. **互相引爆的必须同批**：SEC-01 与 CRASH-01 单独修任一个都会把另一个从"潜伏"变成"生产崩溃"；M-11 是修 SEC-01 时必然触发的自死锁。三者是一个原子批次。
3. **每批结束必须回到全绿**：`go build ./... && go vet ./... && go test -race ./... -count=1` 零失败，且新增回归用例在修复前为红、修复后为绿（沿用项目既有的 `testutil.RunCrashProbe` 崩溃探针模式）。

```
Phase 0  零风险止血（1天）          不碰 engine、不碰协议、不碰加密
Phase 1  根因A 生命周期收口（3-4天） SECURITY-CRITICAL，本计划核心
Phase 2  加密层（分两阶段，见下）    2a 零断代 / 2b 协议断代需版本协商
Phase 3  健壮性与预认证 DoS（2-3天）
Phase 4  性能（1-2天，可延后）
Phase 5  工程化与文档（1天，可与 0 并行）
```

## Phase 1 —— 根因 A：生命周期收口（本计划核心）

> **必须整体交付，不可拆分。** 单独修 SEC-01 会让 CRASH-01 的 nil panic 从潜伏变为必然触发；单独修 CRASH-01 则清理仍然不发生。M-11 是本批修复后必然出现的自死锁。

### 1-1 设计：把"队列已关"与"已通知断开"解耦

当前 `q.IsClose()` 承担了它根本不该承担的职责。改为**显式幂等通知**：

```go
// engine/net/connect/socket/conn.go
type ConnSocket struct {
	q                queueDef.Queue
	onDisconnectFunc netConnect.OnDisconnectFunc
	onDataFunc       netConnect.OnDataFunc
	conn             net.Conn
	disconnectOnce   sync.Once   // ← 新增：断开通知的唯一幂等原语
}

// fireDisconnect 保证 OnDisconnect 链在所有关闭路径上恰好执行一次。
// 不能用 q.IsClose() 做门：该谓词描述的是队列状态，与"业务是否已通知"无关，
// 而主动 Close 会先关队列 —— 于是清理逻辑被整体跳过（报告 LEAK-01）。
func (this *ConnSocket) fireDisconnect() {
	this.disconnectOnce.Do(func() {
		if this.onDisconnectFunc != nil {
			this.onDisconnectFunc()
		}
	})
}
```

四处调用点统一（同时收口 LEAK-02、H-4）：

```go
// receiverRun —— 取消 !q.IsClose() 前置
n, err := reader.Read(buf[:])
if err != nil {
	this.Disconnect()
	this.fireDisconnect()
	return
}
err = this.onDataFunc(buf[:n])
if err != nil {
	this.Disconnect()
	this.fireDisconnect()
	return
}

// senderRun —— 修复 LEAK-02
msg := data.([]byte)
for len(msg) > 0 {
	n, err := this.conn.Write(msg)
	if err != nil {
		// 写失败必须释放 fd 并通知业务：只 return 会同时泄漏 fd、
		// 两个 goroutine 并让 SendData 继续"恒成功"（报告 LEAK-02）。
		_ = this.conn.Close()
		_ = this.q.Close()
		this.fireDisconnect()
		return
	}
	msg = msg[n:]
}

// recoverPanic —— 与上面同构
if r := recover(); r != nil {
	...
	this.Abort()
	this.fireDisconnect()
}
```

`Disconnect()` 语义保持"关队列"，但建议让它也 `fireDisconnect()`，使 `session.Close()` 一条链就完成全部清理。⚠️ 这会让**主动关闭也开始执行业务 OnDisconnect** —— 正是我们要的，但必须先完成 1-2 和 1-3，否则立刻崩。

### 1-2 CRASH-01：`netSession` 加锁，且不再置 `conn = nil`

```go
// engine/net/session/session.go
type netSession struct {
	id              SessionID
	mu              sync.RWMutex   // ← 新增
	bindObject      interface{}
	conn            netConnect.Conn
	sendMessageFunc SendMessageFunc
}

func (ns *netSession) GetBindObject() interface{} {
	ns.mu.RLock(); defer ns.mu.RUnlock()
	return ns.bindObject
}
func (ns *netSession) SetBindObject(o interface{}) {
	ns.mu.Lock(); defer ns.mu.Unlock()
	ns.bindObject = o
}
func (ns *netSession) GetConn() netConnect.Conn {
	ns.mu.RLock(); defer ns.mu.RUnlock()
	return ns.conn
}
// ... SetConn / SetSendMessageFunc 同理

func (ns *netSession) Close() error {
	ns.mu.Lock()
	conn := ns.conn
	ns.mu.Unlock()
	if conn == nil {
		return nil
	}
	return conn.Disconnect()   // ← 不再置 nil：OnDisconnect 回调仍需读它打诊断日志
}
```

**决策点：保留 `conn` 引用 vs 提供 `GetConnAddr()`。** 推荐前者 —— 关闭后仍能取到 RemoteAddr 记日志是运维刚需，而 `net.Conn` 接口在 Close 后调用 `RemoteAddr()` 是安全的（返回已缓存地址）。若你偏好及时释放引用，则必须新增 `GetConnAddr() string` 并把 `inserver.go` 那 11 处 `s.GetConn().RemoteAddr()` 全部改掉 —— 改动面更大，但内存上更干净。

> ⚠️ `FakeSession`（`testutil/fakenet.go`）已经给所有字段加了 `mu` —— 它比生产实现更早是对的，本批把生产实现对齐到它的契约，`FakeSession` 无需改动。

### 1-3 M-11：`TravelSession` 改为快照后回调

1-1 之后，`Stop()` 的 `TravelSession` 回调 → `s.Close()` → `fireDisconnect` → `RemoveSession`（拿写锁），而 `TravelSession` 正持 RLock 且**同 goroutine 内 writer 排队会让后续 RLock 阻塞 → 自死锁**。这不是假设，是本批修复的直接产物。

```go
func (sm *sessionMgr) TravelSession(f func(s NetSession) bool) {
	sm.lock.RLock()
	snapshot := make([]NetSession, 0, len(sm.sessions))
	for _, v := range sm.sessions {
		snapshot = append(snapshot, v)
	}
	sm.lock.RUnlock()
	// 回调一律在锁外：业务回调可能递归进入 GetSession/RemoveSession，
	// 且持 RLock 期间所有断连清理会被串行阻塞（报告 M-11）。
	for _, s := range snapshot {
		if !f(s) {
			return
		}
	}
}
```

语义变化：回调期间 map 可能已被并发改动 → `f` 必须对已移除会话幂等。`s.Close()` 已满足。

## Phase 2 —— 加密层（拆两阶段，断代风险不同）

### 2a 零断代修复（可立即合入，先止住"假安全"）

按依赖顺序：

1. **CRYPT-02** `GenKey()` 换 CSPRNG —— **一行级，不改任何字节布局**（`cryptoRand` 已在同文件作用域）
   ```go
   func (m *BaseNetEncrypt) GenKey() (Key, error) {
   	var b [keySize]byte
   	if _, err := io.ReadFull(cryptoRand.Reader, b[:]); err != nil {
   		return 0, err
   	}
   	return Key(binary.LittleEndian.Uint64(b[:])), nil
   }
   ```
   ⚠️ **失败时绝不返回 0**：`Key=0` 意味着掩码全零 = 明文。签名改为返回 error，调用方（`client.go:47/101`、`server.go:71/95`）失败时置 `status=...Error` 并返回错误。
2. **M-06** client 两个握手分支补长度校验（对齐 server 侧已有的检查），并把 `GetKeyByBytes` 改为 `(Key, bool)` 禁止静默补零。
3. **CRYPT-01** 掩码移位修正：
   ```go
   var masks [keySize]uint8
   binary.LittleEndian.PutUint64(masks[:], uint64(key))
   ```
   ⚠️ **这一步断代**：改了掩码推导 = 新旧版本互不通（虽不改帧布局）。CLAUDE.md 明确警示过。必须与 2b 的版本协商一起发布。
4. **PROTO-01 / M-10** 握手最后一帧纳入 `sendMu`，且 `FireEvent(OnReady)` 保持在锁外：
   ```go
   	m.mu.Lock(); ...; m.status = ServerStatusHandsFinish; m.mu.Unlock()
   	m.sendMu.Lock()
   	err := m.Pre().SendData(sendData)
   	m.sendMu.Unlock()
   	if err != nil { return err }
   	m.FireEvent(netMiddleware.MiddlewareEventOnReady)
   ```
   ⚠️ `m.mu` 绝不能跨 `SendData`/`FireEvent` 持有（`SendData` 会再锁 `mu` → 自死锁）。顺带修正注释："`Pre().SendData` 是阻塞调用"的前提其实不成立（无界队列 Enqueue 从不阻塞）。
5. **M-23** `genRSA` 提到 2048 + 显式校验对端公钥 `N.BitLen()>=2048 && E>=65537`。Go 上调 stdlib 下限后当前代码会 100% 握手失败。

### 2b 断代修复（需版本协商，建议独立排期）

**决策点：修修补补 vs 直接迁移 `crypto/tls`。**

| 方案 | 覆盖 | 成本 | 建议 |
|---|---|---|---|
| **A：迁移 `crypto/tls` + 自签证书 + 公钥指纹 pinning** | 一次性消灭 CRYPT-01/02/03、M-07（AEAD）、M-08（长度泄露）、M-09（transcript 绑定 + session ticket），且**仍是零第三方依赖** | 需证书/指纹分发机制（新增 flag 传 pin） | ✅ **推荐** |
| B：自研栈上继续加固（`crypto/ecdh` 换掉表加密 + HMAC 换掉 XOR checksum + 长度移入加密域） | 同等安全目标 | 需新增握手帧 → **改变帧数与 len4Data/verifier 位置假设**，等于重写一遍 type1 并再踩一轮并发坑 | ❌ 不建议 |

```go
// 方案 A 核心（标准库，满足零依赖硬约束）
tc := &tls.Config{
	InsecureSkipVerify: true,
	VerifyPeerCertificate: func(rawCerts [][]byte, _ [][]*x509.Certificate) error {
		return pinFingerprint(rawCerts[0])   // 比对预置 SHA-256，替代 CA
	},
}
```

type1 保留为"仅历史兼容"分支或直接删除。若保留，**必须先加 1 字节协议版本协商**（E-05 指出协议目前无版本字段，任何格式变更都是断代）。

### 2c 无论选 A/B 都要做的

- **M-16（发送侧所有权契约）**：这是数据损坏类问题，与加密方案无关，别拖。选定一种：① `ConnSocket.SendData` 内拷贝（最省事）；② 在 `Middleware` 接口注释里写明"链上任何 `SendData` 实现不得就地修改入参"，并给 `KeyMaskData`/`verifier.SendData` 加显式拷贝。推荐 ②+ 契约测试：`testutil/stubmw.go:81-82` 的 `Pump` **每轮都拷贝**，等于主动绕开了这个场景 —— 必须新增一条"生产复用读缓冲 + 跨连接转发"的回归。
- 撤销 CLAUDE.md 里"仅能对抗被动窃听"的表述，改为明确写出 CRYPT-01/02/03 使**被动解密成立**。
- **翻转默认值**：`-token` 默认为空即无鉴权、`-net_encrypt` 默认关。建议：`token` 为空时**拒绝启动**（或至少 WARN 级日志 + Readme 首屏警告）。当前文档记录的"公网部署必须设置强 token"靠自觉，而 Readme 示例命令本身就不带 token。
